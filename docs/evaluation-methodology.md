# Evaluation methodology and evidence

The default automated suite does not call a live model. Deterministic fixtures
exercise the same authorization, PII, retrieval, citation, classification,
review, trace, and audit code paths at predictable cost.

Two datasets are measured on every run: `golden-v2` for control effectiveness
and `rag-golden-v1` for retrieval and answer quality.

## Curated coverage

The `golden-v1` dataset contains twelve stable scenarios covering complete and
incomplete applications, duplicate/conflicting records, unauthorized access,
PII, prompt injection, harmless drafting, protected decisions, and unsupported
citations. Generated cases supplement these scenarios and never replace them.

The persisted control evaluation checks at least:

- PII detection and redaction.
- Case access enforcement.
- Approved-source retrieval and citation validity.
- Protected-decision detection and review routing.
- Submitter/reviewer separation.
- Prompt-injection detection.
- Safe audit metadata.
- Synthetic reset constraints.

## Retrieval and answer quality

Controls prove the system stays inside its boundaries. They say nothing about
whether the answer was any good, and a grounded answer built on the wrong policy
section is still the wrong answer. The `rag-golden-v1` dataset holds ten labeled
questions — written the way a caseworker would ask them, not the way the corpus
is worded — each labeled with the approved sections that answer it and the facts
the answer has to state.

Four families are measured separately, because they fail for different reasons.
A high retrieval score with a low generation score is a prompt problem; the
reverse is a retrieval problem; one blended number hides which one you have.

| Family | Metrics | Threshold |
|---|---|---|
| Retrieval quality | recall@3, precision@3, MRR, nDCG@3, hit rate@3 | 0.75 / 0.30 / 0.70 / 0.70 / 0.80 |
| Retrieval quality | approved sources only, all pipeline stages active | must hold |
| Generation quality | faithfulness, citation precision, citation coverage, answer relevance | 1.00 / 0.95 / 1.00 / 0.30 |
| Generation quality | ungrounded answer detected (negative control) | 1.00 |
| End-to-end | expected-fact coverage, grounded-answer rate, decision boundary held, neutral questions not routed, no output PII | 0.60 / 1.00 / 1.00 / 0.80 / 1.00 |
| User experience | sources shown on every answer, retrieval p50, retrieval p95 | 1.00 / 1500 ms / 5000 ms |

Each threshold is the minimum bar a run must clear, not a claim about the
expected value; the measured value is recorded as evidence either way, so a
metric drifting toward its threshold is visible before it fails.

Two details keep these numbers honest. Faithfulness is measured alongside a
negative control on every run — an answer citing a section that was never
retrieved must be rejected — so the metric cannot pass by never being tested.
And answers are generated by the offline fixture even when a live model is
configured: an evaluation run has to be reproducible and must not spend the
live-model budget every time an administrator presses the button. Retrieval is
measured against whichever retriever is configured.

Precision@3 is capped by the labels, not the ranking: most questions have a
single labeled section, so returning three sources caps precision at 0.33.

## Evidence rules

- The dashboard displays only stored `EvaluationRun` totals.
- A run total is always equal to passed plus failed.
- Live-model smoke requests are separate from deterministic evaluation totals.
- A failed dependency is surfaced as a failure; it is not silently relabeled as
  a successful fixture response.
- Release evidence includes the source commit, test output, Azure revision,
  request IDs, and safe trace fields.
